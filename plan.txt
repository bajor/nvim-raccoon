## Definition of exact parity

“Exact parity” means that for the same parsed patch and effective options,
Raccoon produces exactly the same:

1. Context and change groups.
2. Change-block boundaries.
3. Deletion/addition row pairings.
4. Decision to compute or suppress an inline diff.
5. jsdiff change-object sequence.
6. Highlighted UTF-16 ranges on the deletion side.
7. Highlighted UTF-16 ranges on the addition side.
8. Changed text coverage after conversion to Neovim byte columns.

Pixel-perfect browser rendering is out of scope because Neovim uses native
syntax highlighting and extmarks instead of Shiki, HAST, CSS, and the DOM.
Do not describe the result as pixel-identical. It must be semantically exact.

## Required row pairing

Reproduce `iterateOverDiff.ts` exactly.

A contiguous change block containing D deletions and A additions has
`max(D, A)` split rows.

For zero-based row index i:

- Pair deletion[i] with addition[i] when both exist.
- A deletion with no addition has whole-line deletion highlighting only.
- An addition with no deletion has whole-line addition highlighting only.
- Never realign rows by similarity or content.
- Never use `vim.diff` to change this pairing.

Examples:

- 2 deletions and 3 additions:
  - deletion 1 pairs with addition 1
  - deletion 2 pairs with addition 2
  - addition 3 is unpaired

- 3 deletions and 1 addition:
  - deletion 1 pairs with addition 1
  - deletions 2 and 3 are unpaired

This positional behavior is required even when an inserted line appears at the
start or middle of a block.

## Required inline algorithm

For every paired deletion/addition row, mechanically reproduce
`computeLineDiffDecorations` from the pinned release.

Required sequence:

1. Apply the exact `cleanLastNewline` behavior.
2. Measure line length using JavaScript UTF-16 code units, not UTF-8 bytes,
   Unicode code points, display cells, or grapheme clusters.
3. Skip inline decorations when either side contains more than 1000 UTF-16
   code units.
4. A line containing exactly 1000 UTF-16 code units remains eligible.
5. Run `diffWordsWithSpace` from `diff@9.0.0`.
6. Apply Pierre's exact `word-alt` `pushOrJoinSpan` behavior.
7. Preserve the `isLastItem` behavior exactly.
8. Treat `item.value.length === 1` as one JavaScript UTF-16 code unit. Do not
   reinterpret the condition as “one Unicode character” or “one whitespace
   character.”
9. Produce exactly the upstream deletion and addition decorations.
10. Only after upstream UTF-16 spans are complete, convert them to valid
    zero-based, end-exclusive Neovim UTF-8 byte columns.

Do not add a second `diffChars` pass. Pierre's pinned Diffshub default is
`word-alt`, not an automatic word/character hybrid.

Consequently, this example must follow Pierre, even if another result appears
more precise:

-old_timeout = calculate_timeout(config)
+new_timeout = calculate_timeout(options)

Expected strong spans under Pierre's default:

Deletion:
- `old_timeout`
- `config`

Addition:
- `new_timeout`
- `options`

Do not refine `old_timeout`/`new_timeout` to only `old`/`new`.

Character mode may be ported only if an existing upstream option requires it,
but it must not replace the Diffshub default.

## Exact jsdiff port

Vendor the smallest exact source subset necessary to reproduce:

- `diffWordsWithSpace`
- the synchronous Myers traversal
- upstream tokenization
- upstream equality behavior
- upstream tie-breaking
- upstream change-object construction
- `diffChars` only if required for faithfully supporting the upstream option

Mechanically port the algorithm to Lua. Preserve algorithmic control flow and
tie-breaking. Do not rewrite it from memory.

JavaScript semantic details must be explicitly handled:

- JavaScript strings use UTF-16 code units.
- `diffChars` tokenization uses JavaScript `Array.from`, which iterates Unicode
  code points.
- The word tokenizer uses the exact pinned regular-expression character
  ranges.
- CRLF, LF, non-newline whitespace, punctuation, extended Latin, CJK,
  combining marks, and astral characters must match upstream.
- Invalid or unsupported input must not silently produce different spans.

Store or expose the upstream UTF-16 range before byte conversion so tests can
validate both representations.
